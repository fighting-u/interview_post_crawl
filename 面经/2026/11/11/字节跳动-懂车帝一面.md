## 手撕
1. 无重复字符的最长子串；
AI简要思路：滑动窗口法。维护一个哈希集合记录当前窗口内的字符，右指针不断向右扩展直到遇到重复字符，此时左指针右移缩小窗口直至移除重复字符，期间不断更新最大窗口长度。时间复杂度 O(N)，空间复杂度 O(字符集大小)。

## 场景题
1. 设计一个秒杀系统，要求防止超卖，并且在倒计时结束时才允许用户进行秒杀，详细说明关键架构设计；
AI简要思路：核心在于高并发下的库存扣减与请求削峰。①前端通过JS倒计时控制按钮状态，配合Token机制防刷；②网关层做限流、黑白名单过滤；③请求入队（如RocketMQ）异步削峰，按顺序消费；④Redis预扣减库存（Lua脚本保证原子性），失败直接返回排队中或抢购结束；⑤异步消息触发DB最终扣减与订单创建。倒计时控制可通过ZooKeeper/Etcd分布式锁或Redis分布式锁在约定时间点开启流量开关。

## 项目相关
1. 业务系统里的分布式锁如何设计的？作用是什么？
原文回答: ● 业务系统里的分布式锁如何设计的？作用是什么？
AI简要回答：通常基于Redis（SETNX + EXPIRE + Lua或Redisson框架）或Zookeeper实现。作用是确保在集群或多节点环境下，同一时刻只有一个实例能执行特定逻辑（如数据初始化、定时任务），解决资源竞争与数据一致性问题。重点需考虑可重入性、死锁防范（看门狗机制）、高可用与容灾。

2. 异步转存如何设计的？有没有做安全检查？
原文回答: ● 异步转存如何设计的？有没有做安全检查？
AI简要回答：将非核心链路或耗时IO操作放入消息队列异步处理，提升主流程响应速度。安全检查主要包括：①落盘前的数据脱敏/加密；②权限校验与访问控制（仅授权服务可读取）；③完整性校验（Hash/Sig）与防篡改机制；④传输链路的HTTPS/MTLS加密。

3. Agent 项目的 ReAct 如何实现？设计时遇到什么问题，如何解决？
原文回答: ● Agent 项目的 ReAct 如何实现？设计时遇到什么问题，如何解决？
AI简要回答：ReAct (Reasoning + Acting) 循环由“思考→行动→观察→重复”构成。模型根据当前状态输出Thought，调用指定Action（API/工具），拿到Observation后重新输入Prompt循环。遇到的常见问题包括：动作幻觉（乱调接口）、上下文爆炸、死循环。解决策略：①强化Prompt约束与Few-shot示例；②引入Schema严格校验输入参数；③设置最大循环步数限制与安全沙箱拦截无效调用。

4. 有没有在线和离线分别进行评测？Bad Case 调优是怎么做的？
原文回答: ● 有没有在线和离线分别进行评测？Bad Case 调优是怎么做的？
AI简要回答：离线测试构建标准化数据集，评估准确率、召回率与指令遵循度；线上采用A/B测试或灰度放量，监控业务转化率与用户满意度。Bad Case调优主要靠人工标注分析错误类型（是意图识别错、工具选错还是逻辑推理断档），针对性地补充RAG知识库、优化Prompt模板或微调SFT模型。

5. ReAct 如何防止死循环调用？
原文回答: ● ReAct 如何防止死循环调用？
AI简要回答：①硬性阈值：在系统底层设置最大迭代次数（Max Iterations），超限强制终止并降级回复；②状态检测：监测连续多次的Action/Observation是否完全相同，若检测到循环征兆则提前熔断；③Self-Correction Prompting：在Prompt中显式加入“如果尝试X次仍无法完成任务，请直接给出兜底答案”。

6. Agent 的上下文管理如何实现的？
原文回答: ● Agent 的上下文管理如何实现的？
AI简要回答：通常采用滑动窗口截断与摘要压缩相结合。短对话直接追加历史消息；超长会话引入Vector Store检索相关段落，并结合Summarization Layer对早期冗长对话生成压缩摘要，保留关键事实与决策树，从而在有限Context Window内维持连贯性。

7. 用户刚发一条消息，马上再发一条消息，如何保证第二条消息处理时能读到第一条消息的上下文？
原文回答: ● 用户刚发一条消息，马上再发一条消息，如何保证第二条消息处理时能读到第一条消息的上下文？
AI简要回答：采用Session级状态缓存。后端为每个User-ID分配唯一Session Context Buffer。无论消息到达间隔多短，新请求进入时会先从内存/Redis拉取该Session的最新完整History，拼接到新的System/User Prompt中一并下发给LLM，保证上下文无缝衔接。

8. 如果需要将工具调用的结果提供给模型生成最终回答，如何实现？
原文回答: ● 如果需要将工具调用的结果提供给模型生成最终回答，如何实现？
AI简要回答：在ReAct的Observation阶段，直接将工具执行的stdout/stderr或结构化JSON结果作为新的Message（通常是Assistant或System角色）注入到当前的Conversation History列表中，模型在下一次推理时自然会将该结果纳入上下文并生成最终答复。

9. 有没有做断点续传？如果用户给 Agent 发送一条消息后退出聊天框，如何保证消息剩下的部分继续返回给用户？
原文回答: ● 有没有做断点续传？如果用户给 Agent 发送一条消息后退出聊天框，如何保证消息剩下的部分继续返回给用户？
AI简要回答：对于SSE流式响应，前端断开连接即视为丢弃剩余Buffer，常规做法是服务端无法主动推送。若需断点续传能力，需改造为异步任务模式：后台接收消息后转为Long-running Task并存入数据库，每次请求携带TaskID拉取进度或已生成的结果片段，前端轮询或通过WebSocket恢复连接后按断点偏移量补齐缺失内容。

10. 如果用户连续发送多条消息，既有普通消息又有工具调用，如何防止 Agent 响应的消息冲突？
原文回答: ● 如果用户连续发送多条消息，既有普通消息又有工具调用，如何防止 Agent 响应的消息冲突？
AI简要回答：实施严格的FIFO优先级队列与Request-ID绑定机制。所有进入的消息打上唯一的Correlation ID并进入独立Worker线程池或队列串行处理。每个请求的生命周期由其ID隔离，即使并发输入，输出也是按原始请求顺序一一对应写入对应的Channel/Socket流，互不干扰。

## 八股
1. 如何防止 MQ 的消息丢失问题？
原文回答: ● 如何防止 MQ 的消息丢失问题？
AI简要回答：分三个阶段防御：①生产者端：开启Confirm/Ack机制，确保消息成功投递至Broker；②Broker端：配置持久化（磁盘落盘），集群高可用部署避免单点故障丢失未消费数据；③消费者端：关闭自动Ack，仅在业务逻辑完全执行成功后手动Ack，若消费失败则重回队列或进入死信队列人工介入。

2. 如何保证 Redis 和 MySQL 的双写一致性？
原文回答: ● 如何保证 Redis 和 MySQL 的双写一致性？
AI简要回答：常用策略为Cache Aside Pattern（旁路缓存）。更新时先删缓存，再更新DB（应对并发更新导致脏数据）；读取时先查缓存，命中则返回，未命中查DB并回填缓存。极端情况下可采用延迟双删或Binlog订阅组件（如Canal）异步删除缓存，以追求最终一致性。

3. Redis 的热 Key 问题有哪些常见解决方案？
原文回答: ● Redis 的热 Key 问题有哪些常见解决方案？
AI简要回答：①本地缓存：在应用服务端增加Caffeine/Guava等L1缓存分担读压力；②热点探测与多副本：识别热Key后，在多个Redis节点上均衡备份该Key，扩大带宽承载；③过期策略优化：针对大Value采用逻辑过期+后台异步重建，避免物理失效时集中穿透DB造成雪崩。

4. 如何分析慢 SQL 并调优？
原文回答: ● 如何分析慢 SQL 并调优？
AI简要回答：①开启慢查询日志定位Top N耗时语句；②使用EXPLAIN分析执行计划，检查索引是否生效（key列）、是否存在全表扫描（type=ALL）、临时表或文件排序（Using temporary/filesort）；③调优手段：建立合适复合索引、覆盖索引减少回表、改写SQL逻辑（如避免SELECT *、子查询改Join）、合理拆分大事务与垂直/水平分库分表。

5. 多表联查问题有哪些常见解决方案？
原文回答: ● 多表联查问题有哪些常见解决方案？
AI简要回答：①基础层面：确保关联字段建有索引，使用Inner/Left Join替代嵌套循环查询；②应用层面：读写分离与反范式设计，将高频关联字段冗余到一张宽表中彻底取消Join；③存储层面：数据量过大时采用分库分表（ShardingSphere等），通过路由规则或全局表映射解决跨节点关联难题。
